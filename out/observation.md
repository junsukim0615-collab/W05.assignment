# Week 5 관찰 기록

## Task 1
- `/31`, `/32`는 전통적인 서브넷 계산 기준으로 사용 가능한 호스트 범위가 없다고 정하여 `(None, None, 마지막 주소)`를 반환한다. 마지막 값은 API의 broadcast 칸을 유지한 계산상 주소이며, 특히 `/32`의 실제 브로드캐스트 전송을 뜻하지 않는다. RFC 3021의 점대점 `/31` 해석은 이 구현에 적용하지 않았다.
- `10.20.30.70`은 `10.0.0.0/8`, `10.20.0.0/16`, `10.20.30.0/24`, `10.20.30.64/26`에 모두 일치하며, 가장 긴 `/26`의 `lab-rack-2`를 선택한다. 기본 경로 `0.0.0.0/0`까지 포함하면 일치 경로는 총 5개다.
- 동일한 네트워크와 prefix 길이를 다시 추가하면 마지막 next hop으로 갱신한다. 길이만 같고 서로 다른 정상 네트워크는 한 목적지에 동시에 일치하지 않는다. 조회는 저장된 모든 경로를 비교하므로 경로 수 N에 비례하는 O(N)이다.

## Task 2
- 두 Wi-Fi 측정에서 사설 주소(172.16.1.29 → 192.168.0.14), 게이트웨이, 공인 주소(163.152.233.1 → 59.27.56.98)는 바뀌었고 /24 마스크는 같았다. 서로 다른 로컬 서브넷의 주소를 할당받은 결과이며, 측정일도 달라 시간에 따른 변동 가능성은 구분해야 한다.
- 사설 주소와 외부 관측 주소가 달라 일반적인 직접 IPv4 접속에서는 최소 한 단계의 NAT를 뒷받침한다. 정확한 단계 수는 공유기 WAN 및 상위 라우터 설정이 없어 확정하지 않았다.
- 직접 캡처한 Discover는 주소 미할당 상태라 0.0.0.0에서 255.255.255.255로 전송됐다. 동일 Transaction ID의 DORA 네 메시지를 확인했고 임대 시간은 7200초였다. 이번 Ack도 브로드캐스트였다.

## Task 3
- prefix 길이별 해시 테이블과 내림차순 탐색을 사용했다. 경로 수 N에 대해 메모리는 O(N + 33)이다. 5000개 경로에서 참조 객체 크기 합계는 기준 796297 bytes, 개선 652896 bytes였다(sys.getsizeof 재귀 합산, 공유 참조 중복 제외, 프로세스 전체 메모리는 아님). 동일 prefix 중복은 LinearTable처럼 처음 추가한 next hop을 유지한다.
- 조회는 존재하는 길이 L개에 비례하는 평균 O(L), L ≤ 33이다(해시 조회 평균 O(1) 전제). 실제로 7개 길이를 사용했고 질의당 평균 2.6129회, 최대 7회 조회했다. 공식 5000개 경로·20000개 질의에서 오답 0개, 1341.2배 향상으로 strong 기준을 충족했다(`bench.txt`, 실행 환경에 따라 변동).
- 비트 트라이는 최대 32비트 깊이로 예측 가능한 조회를 하므로 하드웨어 파이프라인에 적합하다. Python에서는 딕셔너리 조회가 내부 C 코드로 수행되고, 비트마다 Python 노드를 따라가는 반복 비용이 커서 prefix별 해시가 유리할 수 있다.
